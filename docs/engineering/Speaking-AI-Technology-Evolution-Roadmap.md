## 2. Executive Summary

The current speaking feature already has the correct product skeleton: session creation, WebSocket lifecycle, Part 1/2/3 switching, role-play scenarios, score updates, pronunciation feedback, retry sessions, comparison, persistence, and mobile recovery. The main gap is that the intelligence layer is still deterministic and text-first:

1. The Web client sends `partial_transcript` text over the existing speaking WebSocket.
2. The mobile client uses native speech recognition to produce text and can persist a local recording URI, but the server only receives transcript text.
3. The server estimates Fluency/Lexical/Grammar/Pronunciation with word-count and turn-count heuristics.
4. Follow-up questions and pronunciation heatmaps are generated by static rules and regex-like phoneme patterns.
5. The first diagnostic scoring path uses keyword matching and max-score ratios, so speaking diagnosis is not yet a real oral proficiency assessment.

The recommended evolution is not a full rewrite. The safest path is to keep the existing Fastify REST/WebSocket contract and add an AI orchestration layer behind `SpeakingRealtimeService`. The new AI path should use audio where audio matters, use transcript where transcript is sufficient, and preserve the current rule-based logic as deterministic fallback.

Target pipeline:

```text
Client audio + transcript
  -> ASR / streaming transcript
  -> pronunciation assessment from audio
  -> IELTS rubric evaluator from transcript + acoustic features
  -> coach follow-up generator
  -> structured score_update / coach_question / pronunciation_feedback
  -> existing speaking session store, event log, retry comparison, plan adjustment
```

The evolution should be phased:

1. Phase 1: transcript-based AI evaluator and coach, no client audio contract break.
2. Phase 2: audio segment capture/upload for Web and Mobile, server-side ASR normalization.
3. Phase 3: dedicated pronunciation assessment and real heatmap replacement.
4. Phase 4: low-latency speech-to-speech practice mode through Realtime voice APIs.
5. Phase 5: calibration, offline eval gates, and exam-grade diagnostic mode.

v0.2 correction after technical validation:

1. Audio upload is not only an API contract change. The current server dependency set has no multipart parser or binary upload/storage abstraction, so Phase 2 must explicitly add an ingestion layer, size limits, MIME normalization, and cleanup hooks.
2. Audio artifacts must be deleted with account deletion and speaking-session cleanup. The current account deletion path removes speaking session records only; it does not know about future audio files.
3. ASR capability must be model/API-specific. Timestamp, confidence, diarization, prompt, and logprob support differ by provider and model, so the app must normalize optional capabilities instead of assuming every provider returns every signal.
4. Azure Pronunciation Assessment is technically suitable, but scripted and unscripted assessment return different signals. IELTS free speaking should not treat completeness or reference-text scoring as universally available.
5. Realtime voice mode must pick an authoritative result-sync strategy. A client-side WebRTC session does not automatically write final transcripts/scores into this self-hosted backend.
6. Zod validation is necessary but not identical to provider-side Structured Outputs. OpenAI structured output schemas need a provider-compatible JSON Schema contract and refusal handling.
7. Mobile upload cannot assume `voiceAudioUri` always exists or is readable. It needs an iOS/Android build-profile validation matrix.

## 3. Current Codebase Baseline

### 3.1 Speaking Runtime

Current speaking runtime is centered around `SpeakingRealtimeService.recordTranscript`:

1. It requires a connected speaking session.
2. It stores the incoming transcript as a turn.
3. It calls `estimateScores` or `fallbackScores`.
4. It generates a coach follow-up question.
5. It generates suggestions.
6. It builds pronunciation feedback from transcript tokens.
7. It pushes `coach_question` and `score_update` events.
8. It returns the result to the WebSocket route, which serializes the event payload.

This is a useful integration point because it already has the business state needed by an AI pipeline: `userId`, `sessionId`, `partNo`, `topic`, `taskType`, `scenarioType`, turn number, previous events, score history, and retry source session.

### 3.2 Web Client

`SpeakingRealtimePage.tsx` currently:

1. Creates sessions through `POST /v1/realtime/speaking/sessions`.
2. Opens `WS /v1/realtime/speaking`.
3. Sends `partial_transcript` as JSON text.
4. Receives `coach_question`, `score_update`, `session_end`, heartbeat, and errors.
5. Displays score, suggestions, latency, pronunciation issue counts, task counts, retry comparison, and event count.

Gap: the Web client does not yet capture microphone audio. For AI pronunciation feedback and robust ASR, Web needs `getUserMedia()` plus `MediaRecorder`, or direct WebRTC when using a realtime speech model.

### 3.3 Mobile Client

`apps/mobile/app/speaking.tsx` already contains most mobile-side primitives required for an AI upgrade:

1. Microphone permission handling through `expo-audio`.
2. Speech recognition permission handling through `expo-speech-recognition`.
3. Native recognition with interim/final transcripts.
4. Contextual strings from topic keywords.
5. Recording persistence through `recordingOptions.persist`.
6. Volume events through `volumeChangeEventOptions`.
7. Background interruption and reconnect handling.

Gap: final transcript is sent to the server, but the recorded audio URI is not uploaded to the server as an assessable artifact.

### 3.4 Server Dependencies

`apps/server/package.json` currently contains Fastify, WebSocket, Postgres, and Zod. It has no AI SDK, no speech SDK, and no object-storage client. This reinforces the conclusion that current scoring and feedback are purely local rule logic.

### 3.5 Existing Roadmap Alignment

`docs/engineering/AI-Agent-Task-Breakdown.md` already defines the correct target layers:

1. Agent Orchestrator.
2. Provider Adapter.
3. Policy Guard.
4. Evaluation.

It also explicitly names a speaking coach pipeline: `ASR -> 对话追问 -> 评分 -> 反馈聚合`. This document turns that existing intent into a codebase-specific implementation path.

## 4. Theoretical Basis

### 4.1 IELTS Speaking Is Multicriteria, Not Single-Score Text Classification

Official IELTS speaking materials define four assessment criteria:

1. Fluency and Coherence.
2. Lexical Resource.
3. Grammatical Range and Accuracy.
4. Pronunciation.

The official IELTS speaking format also states that the speaking test has three parts and is assessed by certified examiners across those criteria. The key implication for this product is that an AI speaking system must not treat speaking evaluation as a single transcript score. It needs a rubric decomposition that maps each criterion to observable evidence.

### 4.2 Some Criteria Require Audio, Not Just Transcript

Transcript-only evaluation can support:

1. Lexical range, precision, collocation, paraphrase.
2. Grammar range, accuracy, and sentence complexity.
3. Coherence markers, sequencing, and topic development.

Transcript-only evaluation is insufficient for:

1. Actual speech rate.
2. Silent pauses.
3. Hesitation length.
4. Repair behavior and self-correction timing.
5. Stress, intonation, rhythm, and prosody.
6. Word-level and phoneme-level pronunciation accuracy.
7. Intelligibility under accent and delivery variation.

Therefore, a better speaking system should combine two classes of signals:

1. Linguistic signals from transcript and conversation context.
2. Acoustic and pronunciation signals from audio.

### 4.3 Rubric-to-Signal Matrix

| IELTS criterion | Required signals | Primary source | Suitable AI component |
|---|---|---|---|
| Fluency and Coherence | response length, pause frequency, pause duration, speech rate, filler rate, repair/self-correction, discourse markers, idea sequencing | audio + ASR timestamps + transcript | ASR with timestamps, acoustic feature extractor, LLM rubric evaluator |
| Lexical Resource | topic vocabulary, idiomaticity, collocation, paraphrase, precision, repetition | transcript | LLM evaluator, lexical feature extractor |
| Grammatical Range and Accuracy | clause complexity, tense/aspect accuracy, error density, range of structures | transcript | LLM evaluator, grammar diagnostics |
| Pronunciation | word accuracy, phoneme accuracy, stress, intonation, rhythm, intelligibility, prosody | audio | pronunciation assessment provider, optional acoustic feature extractor |

### 4.4 Formative Learning Feedback Requires Evidence

A useful IELTS practice product should not only return scores. Learners need evidence-linked feedback:

1. What did I say?
2. Which exact phrase, word, or segment caused the issue?
3. Which criterion did it affect?
4. How should I improve it?
5. What should I practice next?

This supports the existing product model: `suggestions`, `pronunciation_feedback`, `task_recommendations`, `retry`, and `comparison`. AI should enrich those fields, not bypass them.

### 4.5 AI Scores Must Be Calibrated, Not Trusted by Default

LLM and speech-provider outputs are estimates. They should be treated as practice feedback unless calibrated against a labelled evaluation set. The production design should include:

1. Prompt/schema versioning.
2. Provider/model versioning.
3. Confidence scores.
4. Fallback reason tracking.
5. Offline evaluation against human-labelled samples.
6. Regression gates before provider/model changes.

This is especially important because the product can influence learner decisions. The UI and documentation should describe AI scores as practice estimates, not official IELTS scores.

## 5. Practical Technology Basis

### 5.1 Web Audio Capture

Browser audio capture should use standard Web APIs:

1. `navigator.mediaDevices.getUserMedia({ audio: true })` to request microphone access.
2. `MediaRecorder` to produce recorded chunks for upload.
3. Optional WebRTC when the target provider supports low-latency bidirectional audio sessions.

Practical implication for this codebase: Web can add audio capture without replacing the existing speaking page. The existing WebSocket can keep business events, while a new upload endpoint handles audio segments.

### 5.2 Mobile Audio Capture

The mobile app already uses:

1. `expo-audio` for recording permissions and audio session mode.
2. `expo-speech-recognition` for native speech recognition and persisted recording output.

Practical implication: Phase 2 can add audio upload around the existing `voiceAudioUri` state instead of reworking mobile recognition from scratch.

### 5.3 ASR

ASR is needed for:

1. Normalized transcripts.
2. Timestamped words or segments.
3. Confidence values.
4. Better cross-platform consistency than device-native recognition alone.

Provider choices must be treated as capability profiles, not simple vendor names:

1. OpenAI Speech-to-text is suitable for server-side transcription and model-driven transcript quality, but timestamp/logprob/streaming behavior depends on the selected model/API. The product must not assume word timestamps or confidences are always available from every OpenAI ASR model.
2. Google Cloud Speech-to-Text is suitable when streaming recognition, word time offsets, phrase adaptation, or cloud speech infrastructure are priorities. Confidence values and word offsets are configuration/provider outputs, not guaranteed fields in every response path.
3. Azure Speech to Text is operationally attractive if Azure Pronunciation Assessment is also used, but Azure's pronunciation-assessment recognizer should not replace standard STT when the product needs the most accurate transcript for free-form speaking.
4. Local Whisper-compatible deployment is useful for privacy-sensitive self-hosted deployments, but it shifts latency, GPU/CPU capacity, model upgrades, and timestamp quality onto the deployer.

The app should not bind its business schema to one ASR provider. It should normalize provider output into `SpeakingTranscriptSegment` with optional capability fields:

```ts
type SpeakingTranscriptSegment = {
  segmentId: string;
  text: string;
  startMs?: number;
  endMs?: number;
  confidence?: number;
  words?: Array<{
    word: string;
    startMs?: number;
    endMs?: number;
    confidence?: number;
  }>;
  provider: string;
  model?: string;
};
```

Phase 2 acceptance must verify the exact provider/model combination selected for `OPENAI_ASR_MODEL`, Google STT, or Azure STT. A provider can be enabled only for the capabilities it actually returns in local integration tests.

### 5.4 Pronunciation Assessment

Pronunciation should be handled by a dedicated speech assessment engine rather than an LLM over transcript. Azure Pronunciation Assessment is a practical candidate because it supports language-learning oriented feedback such as word, syllable, phoneme, fluency, completeness, and prosody-related outputs.

Important caveats:

1. Scripted assessment and unscripted assessment are different product modes. Scripted reading can compare against reference text and produce reference-aligned completeness. IELTS free-speaking answers usually do not have a fixed reference answer, so they should use unscripted assessment or a custom task-specific approach.
2. Completeness must not be used as a general IELTS speaking score in free-response mode. It is meaningful for reading or reference-text tasks, not for open-ended Part 1/2/3 answers.
3. Phoneme, syllable, and prosody details can depend on locale and SDK/API support. The adapter must store the raw provider capability summary in trace metadata.
4. If transcript accuracy is critical, run standard ASR first or in parallel and treat pronunciation assessment text as a pronunciation artifact, not necessarily the canonical transcript.

Practical implication: map provider output into the current `SpeakingPronunciationFeedback` shape:

1. `wordIssues`
2. `phonemeIssues`
3. `replaySegments`
4. `taskRecommendations`

This allows the UI to upgrade from regex-based heatmaps to real audio-derived evidence without breaking the high-level user workflow.

### 5.5 LLM Coach and Evaluator

LLM should be responsible for:

1. Dynamic follow-up questions.
2. IELTS rubric scoring for text-driven dimensions.
3. Evidence-linked suggestions.
4. Retry comparison summary.
5. Role-play behavior.
6. Diagnostic interpretation and learning-plan signals.

LLM should not be the sole source for pronunciation scoring unless no audio provider is available. When no audio provider is configured, it may generate pronunciation advice from transcript only, but the response must mark `pronunciation_source: "transcript_only"` and lower confidence.

### 5.6 Structured Outputs

Model outputs must be schema-bound. The service should use Zod/JSON Schema validation at the boundary and reject or retry malformed AI responses. The current codebase already depends on Zod, so the provider result can be validated before it reaches `SpeakingRealtimeService`.

For OpenAI Structured Outputs specifically:

1. Zod is a local TypeScript validator. The provider call still needs a provider-compatible JSON Schema or SDK helper that converts the Zod schema into the supported JSON Schema subset.
2. Strict structured output schemas should set object shapes explicitly, including `additionalProperties: false` where required by the provider.
3. Refusals, safety stops, and incomplete generations are valid API outcomes and must be handled separately from schema validation failures.
4. Schema versioning must cover both local Zod and provider JSON Schema, because a local-only schema change can silently diverge from the provider contract.

Practical implication:

```text
provider raw response
  -> provider adapter normalization
  -> zod schema validation
  -> business DTO
  -> existing score_update serialization
```

### 5.7 Realtime Speech-to-Speech

Realtime voice APIs can improve practice experience because the learner can speak naturally and receive spoken follow-ups quickly. However, this should be a later phase because it changes the transport and client runtime more than transcript-based scoring.

Recommended pattern:

1. Server issues short-lived provider session credentials.
2. Client connects to realtime provider through WebRTC or provider WebSocket.
3. Provider handles speech-to-speech interaction.
4. The implementation must choose one authoritative result-sync path:
   - server-side provider WebSocket proxy: strongest backend authority, higher latency and server bandwidth;
   - direct client WebRTC plus client-mirrored result events: lowest latency, requires idempotency, signature/session validation, and tamper-aware server reconciliation;
   - provider-side server controls or webhook-like callbacks where supported: best if available, but provider-specific.
5. Existing speaking session remains the system of record.

This preserves self-hosted learning state while using a specialized provider for low-latency voice interaction.

## 9. Structured Output Schema

The first AI evaluator schema should be intentionally narrow. Do not ask the model to generate arbitrary prose.

```ts
export const speakingTurnEvaluationSchema = z.object({
  coach_question: z.string().min(1).max(300),
  scores: z.object({
    fluency: z.number().min(0).max(9),
    lexical: z.number().min(0).max(9),
    grammar: z.number().min(0).max(9),
    pronunciation: z.number().min(0).max(9)
  }),
  criteria_feedback: z.object({
    fluency: z.string().min(1).max(500),
    lexical: z.string().min(1).max(500),
    grammar: z.string().min(1).max(500),
    pronunciation: z.string().min(1).max(500)
  }),
  evidence: z.array(
    z.object({
      criterion: z.enum(["fluency", "lexical", "grammar", "pronunciation"]),
      quote: z.string().min(1).max(160),
      issue: z.string().min(1).max(240),
      action: z.string().min(1).max(240)
    })
  ).min(2).max(6),
  suggestions: z.array(z.string().min(1).max(180)).min(2).max(4),
  confidence: z.object({
    overall: z.number().min(0).max(1),
    scoring: z.number().min(0).max(1),
    pronunciation: z.number().min(0).max(1)
  })
});
```

Provider-side JSON Schema must be generated or maintained from this local schema. The provider contract should be checked into the repository, for example:

```text
apps/server/src/domain/ai/speaking/schemas/
  speaking-turn-eval-v1.zod.ts
  speaking-turn-eval-v1.openai-json-schema.json
```

The JSON Schema version should be included in `providerTrace.schemaVersion`; local Zod-only changes are not enough for a valid provider contract.

Mapping to current response:

1. `scores.*` maps to existing `score_update`.
2. `suggestions` maps to existing `suggestions`.
3. `coach_question` maps to existing `coach_question`.
4. `evidence` can be added to event payload without disrupting existing clients.
5. `confidence` and `providerTrace` should be stored in session events and exposed to debug views.

## 11. REST API Evolution

### 11.1 Audio Segment Upload

Add:

```text
POST /v1/realtime/speaking/sessions/:session_id/audio-segments
```

Server prerequisite:

1. Add `@fastify/multipart` if the contract stays as `multipart/form-data`, or choose a raw binary upload endpoint with explicit metadata headers.
2. Configure maximum file size, maximum request duration, and accepted MIME types before the route is enabled.
3. Normalize browser/mobile codec output into provider-supported input formats when required. Web `MediaRecorder` commonly produces `webm/opus` or platform-dependent formats; mobile recording output may differ by OS and build profile.
4. Persist uploads to a temp location first, validate size/hash/MIME/duration, then move into durable audio storage.
5. Delete temp files on validation failure, provider failure, and request abort.

Payload shape:

```text
multipart/form-data
  audio: File
  part_no: 1 | 2 | 3
  turn_no?: number
  source: "web_media_recorder" | "mobile_expo_audio" | "provider_realtime"
  idempotency_key: string
  content_sha256?: string
  mime_type?: string
  duration_ms?: number
  client_started_at?: string
  client_ended_at?: string
  transcript_hint?: string
```

Response:

```json
{
  "segment_id": "uuid",
  "session_id": "uuid",
  "status": "queued",
  "storage_key": "internal://speaking-audio/...",
  "mime_type": "audio/webm",
  "size_bytes": 123456,
  "created_at": "..."
}
```

The API must not return a public file URL by default. Audio storage keys are internal identifiers; any future playback URL must be short-lived and permission-checked.

```ts
  mimeType: string;
  contentSha256?: string;
  durationMs?: number;
  sizeBytes: number;
  transcriptHint?: string;
  status: "queued" | "validated" | "transcribed" | "assessed" | "failed" | "deleted";
  failureReason?: string;
  createdAt: string;
  deletedAt?: string;
};

type SpeakingAiRunSummary = {
  agentRunId: string;
  taskType:
    | "speaking_turn_text_eval"
    | "speaking_turn_multimodal_eval"
    | "speaking_diagnostic_eval"
    | "speaking_retry_comparison";
  provider: string;
  model?: string;
  promptVersion: string;
  schemaVersion: string;
  latencyMs: number;
  status: "succeeded" | "fallback" | "failed";
  fallbackReason?: string;
  createdAt: string;
};
```

For self-hosted mode, audio storage can start as local filesystem storage with a documented retention policy, then later support S3-compatible object storage.

Add an explicit storage abstraction:

```ts
export type SpeakingAudioStorage = {
  put(input: {
    sessionId: string;
    segmentId: string;
    sourcePath: string;
    mimeType: string;
    contentSha256?: string;
  }): Promise<{ storageKey: string; sizeBytes: number }>;
  read(storageKey: string): Promise<NodeJS.ReadableStream>;
  delete(storageKey: string): Promise<void>;
  deleteBySessionIds(sessionIds: string[]): Promise<{ deletedCount: number; failedKeys: string[] }>;
  sweepOrphans(before: Date): Promise<{ deletedCount: number; failedKeys: string[] }>;
};
```

Account deletion must call `deleteBySessionIds()` before or during removal of speaking sessions. If audio deletion fails, the account deletion response should not silently claim full deletion; it should record a deletion-exception audit entry and expose the same operational follow-up pattern as other deletion exceptions.

## 13. Provider Strategy

### 13.1 Recommended Provider Matrix

| Capability | Primary recommendation | Fallback | Reason |
|---|---|---|---|
| Transcript-based coach/evaluator | OpenAI structured text generation | local rule provider | Best initial quality gain with minimal contract change |
| Batch ASR | OpenAI Speech-to-text, Google STT, or Azure STT after model-level verification | device transcript | Better cross-platform normalization than native-only recognition |
| ASR word timestamps/confidence | Provider/model-specific capability after local proof | transcript only | Do not assume all ASR models return word-level timestamps or confidence |
| Streaming ASR | Google STT or OpenAI Realtime transcription, depending deployment constraints | batch ASR after turn end | Needed for live UI but not required for Phase 1 |
| Pronunciation assessment | Azure Speech Pronunciation Assessment with scripted/unscripted mode selected per task | transcript-only pronunciation advice with low confidence | Dedicated language-learning assessment signals |
| Realtime speech-to-speech | OpenAI Realtime API with explicit sync strategy | current transcript WebSocket mode | Best experience but larger client and cost impact |
| TTS coach audio | OpenAI Audio Speech or Google TTS | text-only coach question | Useful but not required for scoring correctness |

### 13.2 Provider Selection Principles

1. Do not let provider-specific fields leak into public API contracts.
2. Version every prompt, schema, model, and rubric mapping.
3. Use short timeouts and bounded retries on user-facing realtime flows.
4. Preserve deterministic local fallback for demos, self-hosted offline tests, and provider outages.
5. Store enough trace metadata to debug quality regressions.
6. Avoid sending unnecessary profile/account data to AI providers.

## 15. Phase Roadmap

### Phase 0: Groundwork and Evaluation Assets

Goal: prepare AI integration without changing product behavior.

Implementation:

1. Add AI runtime config parser.
2. Add provider interfaces and local rule provider.
3. Add prompt/schema files for speaking turn evaluation.
4. Add `agentRunId`, `promptVersion`, `schemaVersion`, and provider trace types.
5. Add `SpeakingAudioStorage` interface with local no-op or disabled implementation.
6. Decide upload transport: `@fastify/multipart` multipart route or raw binary route.
7. Build a small offline evaluation fixture seed set:
   - Part 1 short answers.
   - Part 2 long-turn answers.
   - Part 3 abstract discussion answers.
   - role-play answers.
   - weak/medium/strong examples.

Acceptance:

1. Existing tests pass with `AI_ENABLED=false`.
2. Local rule provider returns the exact current response shape.
3. Evaluation fixture runner can compare produced scores against expected ranges.
4. Server startup validates any enabled provider/model capability configuration.
5. Audio storage deletion hooks are defined before audio upload is enabled.

### Phase 1: Transcript-Based AI Evaluator and Coach

Goal: replace static scoring/follow-up generation with AI for users who configure a provider.

Implementation:

1. In `SpeakingRealtimeService.recordTranscript`, call `SpeakingAiOrchestrator` after storing the transcript.
2. Prompt the model with:
   - IELTS part.
   - topic and scenario.
   - current transcript.
   - compact prior turn context.
   - target rubric.
   - required structured output schema.
3. Validate model output with Zod.
4. Fall back to current `estimateScores`, `generateFollowUpQuestion`, `generateSuggestions`, and `buildPronunciationFeedback` on timeout/schema/error.
5. Add trace fields to session events.

Code impact:

1. `apps/server/src/domain/speaking-realtime-service.ts`
2. new `apps/server/src/domain/ai/*`
3. `apps/server/src/app.ts` for dependency injection
4. `apps/server/src/index.ts` for env parsing
5. server tests for AI success, timeout fallback, schema failure fallback

Acceptance:

1. Existing Web/Mobile clients continue to work without changes.
2. `score_update` remains backward compatible.
3. AI path returns at least two evidence-linked suggestions.
4. Timeout fallback returns within configured maximum latency.
5. Event logs expose `ai.enabled`, `agent_run_id`, and fallback reason.

### Phase 2: Audio Capture and ASR Normalization

Goal: collect audio so fluency and pronunciation can be evaluated from speech, not only text.

Web implementation:

1. Add microphone permission UI.
2. Use `getUserMedia` and `MediaRecorder`.
3. Record per answer turn.
4. Upload audio segment after user stops recording.
5. Keep manual transcript input as fallback.

Mobile implementation:

1. Reuse `voiceAudioUri`.
2. Upload persisted recording after final transcript event.
3. Include native transcript as `transcript_hint`.
4. Preserve current background interruption/reconnect logic.

Server implementation:

1. Add audio segment upload endpoint and dependency support (`@fastify/multipart` or raw binary route).
2. Store audio segment metadata on speaking session.
3. Add ASR adapter and normalized transcript segments.
4. Add `asr_update` event.
5. Validate size, MIME type, duration, checksum, and idempotency key.
6. Transcode or reject unsupported formats before provider calls.

Acceptance:

1. Web and Mobile can complete a speaking turn by recording audio.
2. Server stores audio metadata and transcript segments.
3. If ASR fails, native/manual transcript still flows through Phase 1 evaluator.
4. Audio retention is configurable.
5. Account deletion removes linked audio artifacts or records an explicit deletion exception.
6. iOS and Android builds prove `voiceAudioUri` file readability across development, preview, and production profiles.

### Phase 3: Dedicated Pronunciation Assessment

Goal: replace regex-based pronunciation heatmaps with audio-derived word/phoneme/prosody feedback.

Implementation:

1. Add pronunciation provider adapter.
2. Normalize provider results into current `SpeakingPronunciationFeedback`.
3. Add replay segment timestamps based on actual audio alignment.
4. Extend task generation with provider severity and recurrence count.
5. Select scripted vs unscripted assessment per task:
   - IELTS Part 1/2/3 free answers: unscripted mode or free-response-compatible scoring.
   - Repeat-after-me or reference reading drills: scripted mode with reference text.
6. Mark pronunciation source:
   - `audio_provider`
   - `asr_timestamps`
   - `transcript_only`
   - `rule_fallback`

Acceptance:

2. `score_update.pronunciation_feedback` remains backward compatible.
3. Confidence is lower when only transcript or rules are available.
4. Regression tests cover provider success and provider fallback.
5. Completeness is not surfaced for free-response IELTS tasks unless the selected provider mode makes it meaningful.

## 17. Quality and Evaluation Plan

### 17.1 Offline Evaluation Set

Build a private seed evaluation set with:

1. 20 Part 1 short responses.
2. 20 Part 2 long responses.
3. 20 Part 3 abstract discussion responses.
4. 10 role-play sessions.
5. 20 pronunciation-targeted clips covering common learner issues.
6. At least two human annotations per sample where feasible.

Each sample should include:

1. Audio file.
2. Human transcript.
3. ASR transcript.
4. Part number and prompt.
5. Human criterion bands or acceptable band range.
6. Known pronunciation issues.
7. Expected feedback themes.

This seed set is not enough for release confidence. Before enabling calibrated score claims, expand it with:

1. Band distribution coverage from 4.0 to 8.0+.
2. Multiple accents and first-language backgrounds.
3. Device microphone variation.
4. Background noise and weak-network scenarios.
5. Short, medium, and long answer lengths.
6. Holdout prompts not used in prompt engineering.
7. Separate scripted pronunciation drills and unscripted IELTS answers.

### 17.2 Metrics

| Metric | Purpose | Suggested gate after calibration |
|---|---|---|
| criterion MAE | score accuracy per criterion | <= 0.75 band on labelled set |
| adjacent-band hit rate | practical score usefulness | >= 85% within +/- 1 band |
| ASR WER | transcript quality | track by client/platform/accent |
| pronunciation issue precision | heatmap usefulness | sample-based QA gate |
| structured output valid rate | schema reliability | >= 99% |
| fallback rate | provider stability | alert if above baseline |
| P95 feedback latency | UX | Phase 1 <= 8s, Phase 4 first response <= 3s target |
| empty/low-action feedback rate | learning quality | alert if above threshold |

### 17.3 Online Observability

For each AI run, log:

1. `agent_run_id`
2. `task_type`
3. provider
4. model
5. prompt/schema version
6. input token/audio duration buckets, not raw PII in analytics
7. latency
8. success/fallback/failure
9. fallback reason
10. validation error category
11. confidence buckets

Do not log raw audio or full transcripts into general analytics. Keep raw learning content inside speaking session storage under the data-retention policy.

The suggested numeric gates are calibration targets, not Phase 0 release blockers. The first implementation gate should require metric collection and no severe regression against the local rule baseline; calibrated thresholds should be enforced only after the labelled set is large enough.

## 18. Security, Privacy, and Compliance

### 18.1 User Consent

Before audio capture or provider processing, the product should clearly state:

1. Microphone access is required for speaking practice.
2. Audio may be processed by configured AI providers.
3. AI feedback is for practice and is not official IELTS scoring.
4. Audio retention depends on the self-hosted deployment setting.

### 18.2 Data Minimization

Provider requests should include only:

1. Current speaking prompt.
2. Transcript/audio segment needed for the turn.
3. Compact previous turn context.
4. Target band or learner goal if needed.

Avoid sending:

1. Email, phone, account identifiers.
2. Full account profile.
3. Unrelated plan/progress data.

### 18.3 Secrets

Secrets must support both direct env and `_FILE` variants, consistent with current server config patterns. Never return provider keys through runtime endpoints.

### 18.4 Minors

Because the mobile app already includes minor/guardian flows, speaking AI should respect the same age-band policy:

1. Extra notice before audio recording for under-18 users.
2. Conservative retention defaults.
3. Account deletion must delete linked speaking audio artifacts.

### 18.5 Audio Deletion Semantics

Audio deletion must be explicit because audio artifacts will live outside the existing `speaking_sessions` payload:

1. User deletion removes speaking session records and calls audio storage deletion for all linked session IDs.
2. If local filesystem deletion fails, record an audit/deletion-exception entry and expose operational remediation.
3. Retention sweeps delete expired audio artifacts and mark linked segment metadata as `deleted` when the session still exists.
4. Orphan sweeps remove files with no linked speaking session after a configurable grace period.

## 19. Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| AI score instability | user trust loss | offline eval gates, versioning, confidence, fallback |
| Pronunciation provider mismatch with IELTS rubric | misleading pronunciation band | calibrate mapping, expose provider source and confidence |
| ASR errors penalize learners unfairly | wrong feedback | retain audio, confidence weighting, allow transcript correction |
| Realtime voice cost spikes | operating cost | feature flag, quotas, fallback transcript mode |
| Provider outage | broken speaking practice | local rule provider fallback and timeout budget |
| Privacy concerns around audio | legal and adoption risk | consent, minimization, retention config, deletion integration |
| Client complexity from WebRTC | delivery risk | ship transcript/audio-upload phases first |
| Prompt injection from learner transcript | unsafe or off-rubric output | guardrail, system prompts, schema validation, output filtering |
